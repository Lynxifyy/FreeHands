UI Preview, code_critique, and code tools

Three additions to Agent Canvas: a right-side drawer tab that renders the UI a coding agent just produced, a client tool that tells the agent "that won't work / that's wrong / that's incomplete", and a settings page for both.

What this PR is

All three ride machinery that already exists in Canvas — the drawer tab registry and the client-defined tool contract — so nothing new is invented on the wire. The only new surfaces are one tab, one client tool, one settings page, and the pure renderers/analyzers behind them.

1. The UI Preview tab

A coding agent writes HTML, SVG, Android XML layouts and Jetpack Compose all day, but Canvas could only show those as source. The Preview tab renders them.

Before

HTML/SVG got a rich preview inside the Files tab. XML layouts and Compose had no preview at all — you read the markup. The agent's show_preview just selected the file in Files.

After

A dedicated Preview tab renders every UI format, with a format badge, the path, auto-refresh, refresh and open-in-new-tab. show_preview routes UI files here; everything else still lands on Files.

Format detection

detectUiPreviewFormat(path, content) is extension-first for the unambiguous cases and content-aware for the two that share an extension:

html / htm          -> html
svg                 -> svg
md / markdown       -> markdown
xml                 -> xml
kt / kts            -> compose  (only when @Composable / setContent is present)
otherwise           -> unknown  (no preview; stays on Files)

The dispatcher needs the answer before reading the file, so previewFormatForPath(path) resolves from the path alone and treats a .kt as Compose — the agent only previews Kotlin it knows is UI. The tab re-runs content-aware detection once it has the body.

Rendering: real for HTML, approximate for XML/Compose

FormatRendererFidelity
HTMLpass-through into a sandboxed iframe (full document untouched, fragment wrapped)faithful
SVGwrapped in a centering documentfaithful
XML layoutxml-layout-transform: containers/widgets → flexbox, @string resolutionstructural, approximate
Composecompose-transform: a narrow Kotlin DSL parser → flexboxstructural, approximate
Markdownescaped preformatted textliteral

The two transformers never silently drop a node: anything they cannot model becomes a labelled placeholder, and every such node is listed in a warning block above the preview. So an approximate render is never mistaken for pixel-accurate output.

// compose-transform output for:
//   @Composable fun X() { Column { Text("hi") } }
<div class="oh-compose-container" data-compose-type="Column"
     style="display:flex;flex-direction:column;box-sizing:border-box">
  <div class="oh-compose-text" style="box-sizing:border-box">hi</div>
</div>
Security. Every preview renders in <iframe sandbox> with no allow-same-origin, so previewed markup cannot reach Canvas state, cookies or the network through the parent. HTML is not sanitized (that would break fidelity); the sandbox is the boundary. Scripts stay disabled unless the user opts in on the Code tools page, and even then the sandbox is not relaxed.

State ownership

useUiPreviewStore is the single owner of the preview target, keyed by conversation so a preview never leaks between conversations. It holds the path, the format, a refresh token and an auto-refresh flag. The tab composes that token with the existing workspace mutation counter, so agent edits re-render the preview exactly like the Files tab already does.

2. code_critique: "that won't work / that's wrong / that's incomplete"

Canvas already registers client-defined tools the browser answers (canvas_ui_control, launch_child_conversation, request_secret). This adds a fourth: a pure static review the agent can ask for before it declares itself done.

Before

The agent finished a UI file and moved on. Malformed markup, unbalanced braces, a Compose call outside @Composable, or a leftover TODO() only surfaced later — at build time or never.

After

The agent calls code_critique on the file and gets a verdict plus line-numbered issues, and acts on them in the same turn.

Analyzers (pure, synchronous, no execution, no network)

LanguageRules
HTMLunclosed / mismatched / unexpected close tags, img without alt, button without an accessible name
Android XMLwell-formedness, missing layout_width / layout_height
Kotlin / Composeunbalanced braces/parens, Compose UI without an androidx.compose import, a composable call in a function not marked @Composable, TODO()
GenericTODO/FIXME markers, not-implemented throws, pass-only bodies

Each finding carries a stable rule id, a severity (error / warning / info), a category, an optional line and a hint. The verdict is fail on any error, warn on any warning, else pass.

{ "verdict": "fail",
  "summary": "Found 2 issues, including at least one error that will not work.",
  "language": "html",
  "issues": [ { "rule": "html/unclosed-tag", "severity": "error",
                "category": "structure", "line": 1,
                "message": "<div> is never closed.",
                "hint": "Add the matching </div>." } ] }

Request / result flow

It reuses the existing client-tool contract exactly: registered in the adapter's client_tools array, matched by a tool_name type guard in the WebSocket context, handled by handleCodeCritiqueAction, and answered by posting a [code-critique] user message (which the chat hides, like the other client-tool results). A replayed call is claimed once via claimClientToolCall. The tool takes a workspace-relative path (read through the runtime file client, cloud and local) or inline code.

The agent-server caches client-tool schemas by name for the life of the process, so a long-running dev server needs a restart before new conversations pick up a changed schema.

3. Code tools settings

The two features have options, so they get one page and one owner instead of hardcoded defaults.

SettingValuesRead by
Critique strictnessrelaxed (errors only) / normal (warnings + errors) / strict (adds notes)handleCodeCritiqueAction → critiqueCode
Preview auto-refreshon / offthe Preview tab's effective refresh token
Preview allow scriptsoff / onthe Preview iframe's sandbox attribute

These are frontend behaviour, not agent settings, so they persist locally (code-tools-settings-store) rather than going on the agent-server wire. The page lives at /settings/code-tools, is listed in the settings nav and the command menu, and has a Reset to defaults action.

4. Task list progress

The Task List tab was a flat list. It now opens with a labelled progress bar and a done/total count, calls out the in-progress task, and folds completed tasks into a collapsible section. useTaskList returns the derived progress (counts, percent, current task id) from a pure computeTaskProgress helper.
